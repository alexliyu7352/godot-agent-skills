# 焦点、输入路径与视觉证据

## 操作路径
本参考只对本次改动涉及的行为选检查。入口、绑定、遮挡、焦点或打开/关闭行为变化时，从相应玩家入口验证受影响路径；场景主导交互可沿“进入场所 → 找到对象 → 打开 UI → 操作 → 关闭”定位，但不是每次必须重走整段旅程。

局部间距或颜色修改，检查相关控件、代表性内容及改变的命中范围即可；不要因此扩大到对话规则、存档、整段城镇旅程或新增设备支持。项目要求人物/物件入口时，仍不能用额外全局按钮规避实际入口缺陷。

## 焦点和层叠
输入相关变化检查 mouse_filter、接收者、遮挡、可见性与禁用状态。仅按项目已支持且本次受影响的设备验证：支持键盘/手柄时才检查对应初始焦点、方向关系和返回路径，不给鼠标专用项目补手柄方案。弹窗关闭行为变化时，确认恢复目标仍有效；不要把焦点交还给已释放/隐藏控件。

只有修改涉及按键生命周期、重复输入、窗口失焦或菜单层叠时，选择对应边界检查，不默认执行全部。涉及等待/取消时确认旧动作失效；关闭控件本身不代表异步动作已取消。

## 分清三个层次
- 直接调用购买方法：证明内部规则，不证明按钮和输入接通。
- `Input.action_press()`：适合依赖动作状态轮询的代码，不触发 `_input()` 事件分发。
- 事件注入或宿主实际点击：验证指定事件路径；仍须确认目标窗口、位置/焦点及输入已被正确消费。

选择当前版本支持的 `Input.parse_input_event()`、测试框架场景运行器或已配置 MCP/桌面工具。不同注入方式不保证完全相同的 OS 输入行为，应明确覆盖边界。不要为工具方便改变游戏生产输入逻辑。

## 截图与录制
无渲染的 headless 检查不证明画面。截图来自本次目标构建/窗口/状态；实际查看而非只看文件大小。动态故障用特定帧或短录像，局部静态改动一张相关图可能足够。记录已查看的内容，不把自动脚本输出“QA passed”当成自己看到过。

视觉检查与规则检查互补：库存数字看似正确，存档仍可能错误；数字正确，玩家仍可能点不到按钮。没有图形能力时交付已完成的逻辑证据，明确可见体验尚未验证。
