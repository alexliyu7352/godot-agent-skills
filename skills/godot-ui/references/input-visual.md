# 焦点、输入路径与视觉证据

## 操作路径
进入场所 → 找到可交互对象 → 打开 UI → 选择/确认 → 得到反馈 → 关闭并恢复操作。测试要覆盖实际入口，不是只把弹窗直接实例化出来。游戏要求通过人物/场景物件交互时，不以额外全局按钮规避入口问题。

## 焦点和层叠
检查 mouse_filter、GUI 输入接收者、遮挡层、可见性与禁用状态。键盘/手柄焦点需要有效的初始位置、可到达的方向关系和返回路径。弹窗关闭后不要把焦点交还给已释放/隐藏控件；按项目规则选择仍存在的目标。

按键释放、长按、连续点击、窗口失焦与返回、菜单层叠可能暴露状态错误。关闭控件不代表正在等待的异步动作已经取消。

## 分清三个层次
- 直接调用购买方法：证明内部规则，不证明按钮和输入接通。
- `Input.action_press()`：适合依赖动作状态轮询的代码，不触发 `_input()` 事件分发。
- 事件注入或宿主实际点击：验证指定事件路径；仍须确认目标窗口、位置/焦点及输入已被正确消费。

选择当前版本支持的 `Input.parse_input_event()`、测试框架场景运行器或已配置 MCP/桌面工具。不同注入方式不保证完全相同的 OS 输入行为，应明确覆盖边界。不要为工具方便改变游戏生产输入逻辑。

## 截图与录制
无渲染的 headless 检查不证明画面。截图来自本次目标构建/窗口/状态；实际查看而非只看文件大小。动态故障用特定帧或短录像，局部静态改动一张相关图可能足够。记录已查看的内容，不把自动脚本输出“QA passed”当成自己看到过。

视觉检查与规则检查互补：库存数字看似正确，存档仍可能错误；数字正确，玩家仍可能点不到按钮。没有图形能力时交付已完成的逻辑证据，明确可见体验尚未验证。
