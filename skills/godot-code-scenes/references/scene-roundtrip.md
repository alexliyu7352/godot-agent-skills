# 场景保存与重载检查

## 先决定是否应使用生成器
手工维护场景以最小 diff 修改。已采用构建器的场景可以继续构建；新增生成器要明确哪些节点由生成器拥有、哪些允许人工编辑。不要用重生成覆盖未知的人工调整。保存前检查磁盘版本与编辑器未保存内容，多个写入者必须串行协调。

## owner 检查
`add_child()` 只建立树关系，不保证子节点会进入 PackedScene。拟保存节点的 owner 应是合法祖先，并与期望的场景所有权一致。程序新建的多层子节点需要逐层检查；根节点自身不设置为自己的 owner。

实例化的子场景是另一种边界：通常仅调整实例根与外层所有者关系，保留内部场景所有权。不要递归重设导入 GLB 或嵌套 PackedScene 的每个内部节点，意外把外部实例展开成大段内联资源。编辑继承或可编辑子节点时按照工程实际结构处理，而非套统一递归函数。

## 检查顺序
1. 在内存结构中列出这次必须保留的节点路径、类型和关键属性；大型实例内部用抽样或明确契约，避免脆弱的全树快照。
2. 调用 pack 并检查 Error。失败就停止，不能继续保存一个坏包。
3. 在允许执行该场景初始化代码的隔离环境重新实例化，检查上述契约。数量比较只能辅助发现丢节点，不能证明路径、类型和引用正确。
4. 保存到经过确认的测试/输出路径并检查 Error。不要用这个检查覆盖玩家存档或其他原始资源。
5. 从磁盘再次加载，避免缓存掩盖文件错误；使用该版本支持的缓存策略或一个干净 Godot 进程。
6. 验证脚本挂载、导出值、资源绑定、信号与必要运行行为。结构检查未触发 `_ready()` 时，不得宣称初始化完成。

## 反例
- 保存返回非 OK，但构建器最后仍 `quit(0)`。
- 节点总数相同，却把“办事人员”绑定成错误脚本。
- 重载仍读到旧 Resource 缓存，误以为新文件有效。
- 所有测试直接调用内部函数，没有从城镇进入该场所。

本方法不要求禁止 preload、构建时信号连接或同项目使用 2D/3D；这些应依据实际加载时机与引擎能力判断。生成场景仍可能执行脚本初始化，不是无副作用检查。
