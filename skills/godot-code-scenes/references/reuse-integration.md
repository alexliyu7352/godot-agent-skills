# 复用与接入：从现有功能找到最小改动点

用于新增或接入一项功能、选择场景拆分方式。修一个已定位的空值或样式不必执行整份清单；不要求扫描全仓库或重新写架构。

## 先沿一条能工作的路径查找
找到项目中最接近的已完成功能，从实际场景入口追到信号/方法、状态读写者、显示刷新。查看相关 `.tscn` 的实例引用、脚本的调用方，再看 `project.godot` 中有关的 Autoload/插件；不是只凭文件名判断没有现成能力。

若使用插件，读取实际 `addons/<name>/plugin.cfg`、插件版本/提交、本项目已工作的调用及对应版本示例。插件存在不等于已启用，也不等于符合新需求。只有缺口已确认才调查外部替代；检查引擎/语言兼容、维护状态与许可证，不在已有工程中自动安装多个同功能插件。

| 现有能力与需求的差距 | 优先处理 | 不要默认做 |
|---|---|---|
| 只是内容、外观、数值不同 | 新数据/Resource、导出属性、Theme variation | 复制整套脚本或重建对话/交易系统 |
| 多个对象需要同一独立行为 | 复用现有子场景或组件，由拥有者提供依赖 | 为只有一次的两节点组合创建框架 |
| 相同节点结构的稳定变体 | 考虑继承场景；核对基类节点改名的影响 | 用很深的继承树表达所有职业 |
| 结构不同，仅部分规则相同 | 组合组件或共享规则服务 | 因看起来相似强制同一根场景 |
| 插件已有功能，只有项目接口不同 | 小范围配置或适配，保留原状态归属 | 为适配器再建第二份库存/任务/时间状态 |
| 确有不满足的职责 | 把新实现限制在该缺口，说明替代成本 | 顺便迁移整个项目或改引擎版本 |

拆分依据是复用、职责和共同变化，不是“超过15个节点必须拆”。保留当前手工场景或生成场景的维护方式，不因技能示例采用另一种方式就重写。

## 初始化顺序是接口的一部分
动态实例化时，`PackedScene.instantiate()` 返回的节点树尚未必进入 SceneTree。普通配置值和依赖可以在 `add_child()` 前赋值；但 `@onready` 尚未初始化，依赖树的调用不能提前做。

将节点加入已经运行的树可能立即执行生命周期回调，且子节点的 `_ready()` 先于父节点。若子组件在 `_ready()` 读取依赖或发出初始信号，应在入树前完成普通字段注入和必要订阅，或使用明确的初始化握手。不能在父 `_ready()` 才赋值、却假定孩子此前没运行。

典型顺序（不是可直接粘贴的项目 API）：

```text
实例化 → 设置不依赖树的配置 → 订阅不能漏掉的初始事件
       → 加入场景树 → 在自身已就绪后操作 @onready/布局
```

`configure()` 能否入树前调用，取决于其正文是否访问就绪节点；方法名字不能证明它安全。编辑器序列化的依赖优先保留。UI 首次布局和一次渲染完成也不等于 `_ready()` 的同一时刻。

## 对象通信：按语义，不按教条
命令需要明确的接收方和结果，例如交易服务返回成功或失败；状态变化信号通知已发生的事实。父场景可以调用子组件接口，也可以连接兄弟组件之间的信号，没必要把一切送进全局 EventBus。

跨场所通知可沿用既有事件总线，但必须明确数据身份、订阅生命周期和通知时刻。可卸载对象的长期引用慎用；组广播适合通知，不适合依靠“最后一个接收者”决定一次扣款是否成功。

例：商人交互复用现有目标系统 → 传入商人 ID 打开现有交易视图 → 交给唯一交易服务结算 → 视图读结果刷新。只修改店铺表现时不新增经济模拟；只修改结算时不重做商铺美术。

## 接入完成的证据
检查实际入口、一次成功和本次改动涉及的失败路径，确认调用了正确组件，关闭/重开没有重复连接或丢状态。只有涉及存档结构才追加迁移；需要同步修改的接口写进项目原有文档，不在技能里复制一份项目架构。
