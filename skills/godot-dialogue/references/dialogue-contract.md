# 对话状态契约

## 运行时状态
沿用项目的表现方式，但明确：当前节点、有效选项、是否等待输入、是否正在提交效果、是否结束/取消。UI 根据运行器的有效状态显示；不要一个地方按过滤后选项判断，另一个地方仍按原始列表判断。

## 零选项必须有行为
先区分没有选项的普通台词与“定义了选项但全部条件不满足”。后者按设计执行 fallback 台词/节点、返回或结束。允许玩家取消可以是兜底，但不能替代设计要求必须可继续的主线。

边界 fixture：两个选项分别要求声望达标和携带任务物品；玩家两项都不满足。期望有明确反馈与退出/返回路径，不能出现没有按钮且 continue 被拒绝的状态。

## 提交时条件与副作用
显示菜单时得到的结果可能过期。提交时重新验证人物、任务阶段、库存和场景状态；不满足则刷新选项或给出明确反馈。不能先发奖励再检查任务是否还能提交。

区分节点进入、文字播放、选择确认与效果提交。快进文字不提交两次；重新打开不再次发放一次性奖励。成功提交后才发对外状态变更通知。动作身份与持久任务完成状态要能在保存恢复后保持语义。

## 取消、离开与重入
明确取消是否回滚尚未提交的动作；已提交的动作不能仅因动画取消而偷偷撤销。NPC 消失、场所切换、人物死亡等使上下文失效时停止旧对话实例，防止 await 后写回新会话。

用实例世代/会话标识丢弃过期回调，或使用已有取消机制；不要额外建立网络式会话系统解决一个本地 UI 问题。

## 验收用例
正常分支；零有效选项；显示后条件变化；重复确认；快进/退出；NPC 被卸载；自动跳转循环；相关进度保存后重新启动恢复。每个用例写明最终节点和状态变化，不只断言屏幕出现一句文本。
