# 数据定义、实例状态与表现

## 三层不是三个新框架
可用现有项目结构表达以下职责，无需为了命名重新组织全部目录：

| 数据类别 | 例子 | 修改与生命周期 |
|---|---|---|
| 定义 | 物品模板、职业条件、城镇基础配置 | 通常作为共享只读内容，有稳定定义 ID |
| 权威运行状态 | 人物所在位置、库存、关系、任务阶段 | 由明确服务/对象拥有，离开场所后继续存在 |
| 派生表现 | 当前可交易列表、人物头像、节点位置 | 从状态生成，按规则失效和刷新，不另存一份互相竞争的权威值 |

Resource 可以作为数据定义，也可以承载适合的逻辑；重点是共享性与写入边界，不是文件后缀。模板的数组/字典/子资源也可能共享，测试实例 A 的修改是否意外改变 B。

## 实体身份
持久 ID 与显示名分离。历史人物同名、改名、多语言或排序变化，都不应改变身份。定义 ID 与运行实例 ID 区分，例如同一种物品的多个有独立耐久度实例。引用必须能检测缺失和重复。

重命名或合并定义时，有保存兼容需求才设计映射/迁移。不要把编辑器节点路径直接当成数年维护中永远不变的世界身份。可选引用缺失如何降级，应按游戏设计定义。

## 离屏世界
场景树表示当前加载的表现和生命周期，不保证包含全部世界。离开城镇后仍需结算的人物、行动、任务状态由比场景更长寿的状态层持有。加载场景时投影状态，卸载时不依赖 `_exit_tree()` 才临时抢救权威数据。

性能需要分层模拟时，明确“远处按日结算，近处按行动结算”等精度规则及边界转换。不要在没有设计授权时改变模拟精度以追求性能。

## 一致性检查
对本次涉及的内容检查唯一 ID、引用存在、数值范围、互斥状态和派生值重建。增加测试 fixture 覆盖两实例共享模板、场景卸载重载、未加载实体被引用。打印错误后跳过关键实体不能算成功。
