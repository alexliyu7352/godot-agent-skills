# 跨系统结算与时间

## 一个动作的最小契约
直接在已有设计/任务说明中记录，不强制新增文档模板：
- 发起者与动作 ID、读取哪些条件、允许在哪个时间/场景状态提交。
- 应一起成功的写集合，以及失败时哪些状态保持不变。
- 通知发送时刻、重复输入/重试如何处理、结算是否推动游戏时间。

例如购买 3 件单价 10 的商品：验证数量、钱、库存、背包约束和交易仍有效；同次结算扣钱、减少商人库存、增加玩家物品。一次写入失败时不能只回滚 UI；应避免产生部分权威状态，或按既定事务策略可靠恢复。

UI disable 是体验措施，不是防重的唯一机制。重复鼠标事件、任务重入、恢复保存或延迟请求均可能再次提交。一次性奖励用完成状态/动作 ID 保证重复不会重复发放。普通购买允许多次时，不要误用同一 ID 阻止合法连续购买。

## 时间推进
列出一次推进中需结算的事件及顺序：出发、消耗、到达、任务期限、关系/经济更新。相同时刻的排序要稳定且符合设计。大跨度推进不能简单漏掉中间关键事件；要么逐事件处理，要么使用经过验证的等价聚合。

游戏时间、墙上时钟、物理帧、UI 动画时间是不同概念。暂停菜单、倍速、低帧率不能无意改变规则。异步显示完成不等于状态结算完成；存档必须选择明确的安全边界。

## 并发与通知
即使单线程，信号回调和 await 也会造成重入。提交前读取的条件可能已失效；应在提交点重验相关版本/状态。先提交一致状态再发观察通知，避免订阅者看见半完成交易。

多个 agent 开发不同模块时，先共享接口契约与文件归属；不要同时编辑核心状态文件，也不要让不同实现各自增加第二套时间服务。

## 按改动选择检查
| 改动 | 本次需要的检查 |
|---|---|
| 扣款、发物品或奖励的写集合 | 正常结算、条件不足时全部不变、相关重复提交 |
| 提交前存在等待或允许退出 | 显示后条件变化、取消与过期回调 |
| 推进时间或期限判定 | 临界时刻、跨期限、大跨度与顺序 |
| 持久身份或恢复逻辑 | 保存后重新启动，确认幂等与状态连续 |
| 只改列表呈现 | 相关显示和输入；不重跑交易/存档全矩阵 |

检查相关写集合与失败不变性，而不只是“函数返回 true”。不要求每次修改执行表中全部项；已有有效证据沿用。采用随机用例时保留种子/序列以便复现。
