# 写入与恢复失败检查

## 文件写入步骤
在目标同一文件系统的临时路径写完整候选内容，检查打开、写入、flush/关闭和替换结果。失败保留最后一个已确认有效版本。使用固定临时名时要避免两个写入者互相覆盖；不默认启用并发保存。

临时文件加重命名只是构建可靠保存的部分。目标已存在时的 rename/replace 行为、原子替换与断电持久化随平台和文件系统不同；需要查目标平台语义并测试。`FileAccess.flush()` 不应被描述成保证目录项与所有数据已跨断电持久化。

项目需求包括崩溃恢复时，选择与复杂度匹配的策略：已验证备份、双槽/世代标记或平台可靠替换。不是每个小游戏都需要日志系统，但不能删除原档再写新档而声称原子。

## 恢复决策
启动时检测未完成临时文件，只对可验证内容作恢复候选，不按修改时间盲目覆盖。备份也必须解析/版本/不变量验证。恢复来源应可追踪，损坏原件保留用于诊断。

读取未来版本或失败后，禁止紧接着用默认状态自动保存到原槽位。已完成的旧文件不能被“恢复失败，创建新游戏”流程静默覆盖。

## 故障注入矩阵

| 故障 | 预期 |
|---|---|
| 无权限/目录无效/磁盘满 | 返回 I/O 失败，原有效档可用 |
| 临时写入中止 | 不提交半文件；下次启动按恢复规则处理 |
| 替换失败 | 不把失败伪装成成功，不先删唯一有效原档 |
| 截断/格式错误 | 不污染当前世界，保留文件并明确失败 |
| 未来版本 | 拒绝且原字节不变 |
| 关键实体/资源缺失 | 恢复失败或明确设计的降级，不静默跳过 |
| 进程完全退出后重启 | 状态和关系与保存时一致，而不靠旧缓存 |

测试使用隔离用户数据目录和固定 fixture，别拿玩家真实存档做破坏性故障注入。真正断电持久化未测时明确限制。
